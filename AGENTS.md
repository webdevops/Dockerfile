# Agent instructions

## Keep the documentation up to date

The documentation is part of every change. A pull request that changes what users of the images see also updates the documentation **in the same pull request**. Never leave it for a follow-up.

Where the documentation lives:

| File | Content |
| --- | --- |
| `README.md` | Entry point: short intro, quick start, build process, supported tags ("Debian PHP" / "Alpine PHP") |
| `docs/README.md` | Image overview and how the images build on each other (Mermaid diagram) |
| `docs/environment-variables.md` | Every environment variable with its default and effect |
| `docs/customization.md` | Commands, scripts at start and build time, services, cron jobs, application user |
| `docs/images/*.md` | One page per image family: tags, base image, services, settings, development variant |

### When to update it

Update the documentation whenever a change touches any of these:

- an environment variable or `php.*` / `fpm.*` setting (added, removed, renamed, new default, new effect)
- a published image or tag, for example a new or dropped PHP version
- a base image or operating system version
- a PHP extension that is added or removed
- a service, hook directory, entrypoint command or helper tool such as `docker-service`
- the build process, the CI workflow or the commands in the README

### How to update it

1. **Find the source of truth.** Check the code, not older documentation:

   | Question | Where to look |
   | --- | --- |
   | Published images and tags | `-t "webdevops/..."` tags in `.github/workflows/build.yaml` (generated by `ci/console github:generate-ci` from `conf/console.yml` and `ci/`) |
   | Base image | `FROM` line in `docker/<image>/<tag>/Dockerfile` |
   | Variables and defaults | `ENV` in `template/Dockerfile/**` and `docker/**/Dockerfile.jinja2`, scripts in `provisioning/**/bin` and `provisioning/**/provision` |
   | Which files end up in which image | `conf/provision.yml` |

2. **Change sources, not generated files.** `Dockerfile` and `conf/` under `docker/` are generated. Edit `Dockerfile.jinja2`, `template/` or `provisioning/` and run `make provision`.

3. **Verify every statement in a running container.** Build the image (or use the image the CI built) and try the option. Do not rely on reading the scripts alone. Examples:
   - PHP settings: `php -r 'echo ini_get("memory_limit");'`, or `php-fpm -i` for values the CLI overrides
   - PHP-FPM settings: `php-fpm -tt`
   - Web server settings: an HTTP request against the container, or the rendered configuration under `/opt/docker/etc/nginx` or `/opt/docker/etc/httpd`
   - Service options: the command line of the running process
   - Hooks: a script that writes a marker file, then check the marker

   Check every image a statement names, not just one representative: images differ in what they inherit (for example `cli` only works where `APPLICATION_USER` is set). Check both the Debian and the Alpine variant whenever their implementation differs (separate files under `provisioning/*/alpine`, apk vs. apt, `httpd` vs. `apache2`, `crond` vs. `cron`). Test examples with the exact command you document, and make sure a check cannot pass on an error message.

4. **Document only what works.** Never describe an option that has no effect as working. Fix it, or leave it out and open an issue. If it works only in some images, say exactly which.

5. **Keep lists in sync.** The tag lists in `README.md` and in `docs/images/*.md` must match the tags pushed by `.github/workflows/build.yaml`. `webdevops/php-official` is not listed in the README; it is built from the same Dockerfiles as `webdevops/php`. The defaults in `docs/environment-variables.md` must match what a container reports.

6. **Follow the style.**
   - English, GitHub Markdown, relative links, diagrams as Mermaid. No documentation tooling.
   - Usage examples use `docker compose`, not `docker run`.
   - Change the README only where needed; keep its structure and wording.

7. **Say how you verified it.** In the pull request description, list each documented change and the check that confirmed it.
