# Agent instructions

## Repository map

| Path | Content |
| --- | --- |
| `template/` | Shared Twig templates for the Dockerfiles: the layout, which writes the header, and the macros (source) |
| `docker/<image>/<tag>/Dockerfile.twig` | Per-image Twig template; the layout includes it, and it imports the macros it uses from `template/Dockerfile/` (source) |
| `provisioning/` | Scripts and configuration files copied into the images (source); `conf/provision.yml` says which go where |
| `docker/<image>/<tag>/Dockerfile`, `docker/<image>/<tag>/conf/` | Generated by `ci/console generate`, never edited by hand |
| `ci/` | PHP generators behind `ci/console generate`: the Dockerfiles (`generate:dockerfile`), their `conf/` (`generate:provision`), `.github/workflows/build.yaml` (`generate:github-ci`) and the README banner (`generate:readme-banner`) |
| `ci/tests/` | PHPUnit tests of `ci/src`; `ci/tests/Fixtures/repository` is a small repository they run against |
| `ci/grumphp.yml`, `ci/phpstan.neon`, `ci/rector.php`, `ci/fractor.php` | Checks of the PHP code in `ci/`, from pluswerk/grumphp-config |
| `conf/readme-banner.yml`, `ci/resources/readme-banner/` | Texts and font outlines of the README banner (source) |
| `docs/assets/readme-banner-*.svg` | README banner, generated by `ci/console generate:readme-banner`, never edited by hand |
| `tests/` | serverspec (Ruby) and container-structure-test definitions run by the CI |
| `docs/` | User documentation |

`docker/php/<version>` are symlinks to `docker/php-official/<version>`, kept by `ci/console generate:dockerfile`; both images are built from the same Dockerfiles. The tags that are built are the `-t "webdevops/..."` lines in `.github/workflows/build.yaml`.

## Build and test

Only these commands are known to work:

- `make generate` installs the PHP tools of `ci/` and runs `ci/console generate` in `webdevops/php:8.4-alpine`, which regenerates `docker/`, `.github/workflows/build.yaml` and the README banner. Run it after every change to `template/`, `provisioning/`, `conf/` or a `Dockerfile.twig`, and commit the result; the CI fails if a generated file is out of date or missing.
- `docker build -t webdevops/<image>:<tag> docker/<image>/<tag>` builds one image; its parent and `webdevops/toolbox` come from local images or Docker Hub.
- `./build-local.sh [version]` builds all PHP images of one version.
- `make check` installs the PHP tools of `ci/` and checks the PHP code in `ci/` with GrumPHP: coding standard, PHPStan, Rector, `composer audit` and the PHPUnit tests. Run it after every change to `ci/`. GrumPHP and PHPStan only check files that Git knows (`git ls-files`), so `git add` new files first; PHPUnit runs every test anyway. `make test` runs only the tests. Changes to `ci/src` come with tests.
- `make generate`, `make check` and `make test` run as your user, so the files they write belong to you. Do not write into the checkout as root.

Besides `generate`, `check` and `test`, the Makefile has `structure-test`. `make structure-test` runs container-structure-test against your local images of `bootstrap`, `base`, `base-app`, `php`, `php-dev` and `php-nginx`, the images that have a suite in `tests/structure-test`. It tests only the tags in `.github/workflows/build.yaml` and fails if a test fails, if `docker` fails or if no such image exists locally; run it inside `webdevops/dockerfile-build-env` with the Docker socket mounted. The CI runs serverspec for every image except `toolbox` and `dockerfile-build-env`, and container-structure-test for the six images above; to check a change by hand, start the image and try it as described below.

### Packages come with tests

A pull request that adds a package or a tool to an image also adds a test for it, in the same pull request:

- Add a shared example to `tests/serverspec/spec/shared/` that runs the tool and checks its output, not only that the file exists, for example `misc::file` in `tests/serverspec/spec/shared/misc/tools.rb`.
- Include it in the collection of every image that gets the package; for all PHP images that is `collection::php` in `tests/serverspec/spec/collection/php.rb`.
- Check that the test fails on an image without the package and passes on one with it.
- In the pull request description, say how much bigger the images get: absolute and in percent, on average over the images that get the package.

## Keep the documentation up to date

The documentation is part of every change. A pull request that changes what users of the images see also updates the documentation **in the same pull request**. Never leave it for a follow-up.

Where the documentation lives:

| File | Content |
| --- | --- |
| `README.md` | Entry point: short intro, quick start, supported tags ("Debian PHP" / "Alpine PHP") |
| `CONTRIBUTING.md` | Build process: the generated files and `make generate`, the CI and `make check`, building and testing locally, PHP extension builds |
| `docs/README.md` | Image overview, platforms and nightly updates, how the images build on each other (Mermaid diagram) |
| `docs/environment-variables.md` | Every environment variable with its default and effect; uploads and long requests |
| `docs/customization.md` | Commands, scripts at start and build time, tools for your Dockerfile, services, cron jobs and their time zone, healthcheck, configuration files and placeholders, supervisord, locales, application user and changing its UID |
| `docs/images/*.md` | One page per image family: tags, base image, services, settings, development variant. `php.md` also has Debian or Alpine, production, installing extensions, mail and Xdebug with an IDE |
| `docs/known-issues.md` | Options and tools that do not work, with affected images and workaround; migration from older images |
| `docs/discontinued-images.md` | Replacements for images that are no longer built (`storage`, `vsftp`, `ssh`) |

### When to update it

Update the documentation whenever a change touches any of these:

- an environment variable or `php.*` / `fpm.*` setting (added, removed, renamed, new default, new effect)
- a published image or tag, for example a new or dropped PHP version
- a base image or operating system version
- a PHP extension that is added or removed
- a service, hook directory, entrypoint command or helper tool such as `docker-service`
- the build process, the CI workflow or the commands in `CONTRIBUTING.md`

### How to update it

1. **Find the source of truth.** Check the code, not older documentation:

   | Question | Where to look |
   | --- | --- |
   | Published images and tags | `-t "webdevops/..."` tags in `.github/workflows/build.yaml` (generated by `ci/console generate:github-ci` from `conf/console.yml` and `ci/`) |
   | Base image | `FROM` line in `docker/<image>/<tag>/Dockerfile` |
   | Variables and defaults | `ENV` in `template/Dockerfile/**` and `docker/**/Dockerfile.twig`, scripts in `provisioning/**/bin` and `provisioning/**/provision` |
   | Which files end up in which image | `conf/provision.yml` |

2. **Change sources, not generated files.** `Dockerfile` and `conf/` under `docker/` are generated. Edit `Dockerfile.twig`, `template/` or `provisioning/` and run `make generate`.

3. **Verify every statement in a running container.** Build the image (or use the image the CI built) and try the option. Do not rely on reading the scripts alone. Examples:
   - PHP settings: `php -r 'echo ini_get("memory_limit");'`, or `php-fpm -i` for values the CLI overrides
   - PHP-FPM settings: `php-fpm -tt`
   - Web server settings: an HTTP request against the container, or the rendered configuration under `/opt/docker/etc/nginx` or `/opt/docker/etc/httpd`
   - Service options: the command line of the running process
   - Hooks: a script that writes a marker file, then check the marker

   Check every image a statement names, not just one representative: images differ in what they inherit (for example `cli` only works where `APPLICATION_USER` is set). Check both the Debian and the Alpine variant whenever their implementation differs (separate files under `provisioning/*/alpine`, apk vs. apt, `httpd` vs. `apache2`, `crond` vs. `cron`). Test examples with the exact command you document, and make sure a check cannot pass on an error message.

4. **Document only what works.** Never describe an option that has no effect as working. Fix it, or leave it out and list it in `docs/known-issues.md`. If it works only in some images, say exactly which. Anything `docs/known-issues.md` lists as not working must never appear as working anywhere else. An `ENV` line or a script that reads a variable is no proof that it works: `SERVICE_POSTFIX_OPTS` is passed to `postfix start`, which ignores it. When you fix a known issue, remove its entry in the same pull request.

5. **Keep lists in sync.** The tag lists in `README.md` and in `docs/images/*.md` must match the tags pushed by `.github/workflows/build.yaml`. The README banner follows the built tags by itself when you run `ci/console generate:readme-banner`; change its texts in `conf/readme-banner.yml`. `webdevops/php-official` is not listed in the README; it is built from the same Dockerfiles as `webdevops/php`. The defaults in `docs/environment-variables.md` must match what a container reports.

6. **Follow the style.**
   - English, GitHub Markdown, relative links, diagrams as Mermaid. No documentation tooling.
   - Usage examples use `docker compose`, not `docker run`.
   - Change the README only where needed; keep its structure and wording.

7. **Say how you verified it.** In the pull request description, list each documented change and the check that confirmed it.
